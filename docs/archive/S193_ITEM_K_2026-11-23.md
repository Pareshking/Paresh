# S193 item K: link audit, 23 Nov 2026

The crawler is `k_crawl.mjs`, in this folder. It can be moved into `scripts/` unchanged: it imports
`./_settle.mjs` and falls back to the repo's copy. To run it:
`node scripts/k_crawl.mjs http://localhost:8501/ --out artifacts/links [--jobs 4] [--cap 25] [--no-external]`.
It exits 1 when any check fails, and writes `k_links.json` (every link it saw) and `k_results.json`
(every check, every failure, the time each page took).

**What was run.** The app was a frozen copy of the repo at commit `1d61647`, started with
`streamlit run app.py --server.port 8630 --server.headless true`. It ran on the release files
without R2 keys, so some figures can differ from the live site. Pages were read at 1400 px.

**Coverage.**
- Systems: 750, 1000 and `nano` (the > ₹2,000 Cr list).
- Pages on each system: Dashboard, Actions, Portfolio, Screener, Market, Sectors, Indices, Backtest,
  Guide, Watchlist (`?wl=TCS,RELIANCE`) and Configuration.
- Stock pages, each on all three systems: RELIANCE; KPL (ranked only in the 1000); SPECTRUM (ranked
  only in the list). KPL and SPECTRUM were chosen by the crawler from the rows of each system's
  Screener table.
- That makes 42 source pages and 3,338 links. Links were deduped by (page, system, href pattern),
  which left 97 clicks, 190 section-id checks and 3 external links.

## Failures

### F1. A stock opened from a table frame off the Screener: Back loops on the stock (13 of the 16 d-failures)

The clicks that fail:
- Actions, on all 3 systems: a row of the qualified table (SHREEJISPG, or SPECTRUM on nano).
- Sectors, "Stocks in a sector", on all 3 systems: the row, and the symbol link inside it (PVRINOX,
  WELSPUNLIV, SPECTRUM).
- Watchlist, on 750 and 1000: the row, and the link "RELIANCE 195 places past the 40th".

What happens:
1. The click lands on `/actions?stock=X` (or `/sectors`, `/watchlist`).
2. `app.py` redirects that address to `/screener?stock=X`, adding a history entry.
3. Back returns to `/actions?stock=X`, which redirects again.

Three Backs in a row stay on the stock (probed with a navigation log). This is the pre-launch fault
U1 again, by another route.

**Code.**
- `src/ui/screener_table.py:550-553`: `openStock()` sets the host's `window.location.search = '?stock=…'+SYS`.
  That keeps the host's path instead of going to the Screener. The row's own
  `<a href="screener?stock=…">` (`:325`, built by `stock_href`) is never followed, because the click
  handler (`:557-562`) calls `preventDefault`.
- The redirect is `app.py:1310-1314` (`st.switch_page`, which pushes a history entry).
- The Screener itself passes, because its path is already `/screener`.

**Proposed fix (by rule).** `openStock` navigates to the row's own href, resolved against the host:
`host.location.href = new URL(a.getAttribute('href'), host.location.href)`. The one address built by
`stock_href` is then the only stock address.

A test should fail on any `location.search=` in the frame scripts. The crawler's d-check covers the
rest in CI.

### F2. Sectors "Size, and where momentum works →" goes through a redirect (3 c-failures and 3 d-failures, all systems)

The link is `dashboard#s-size` (`dashboard?sys=…#s-size` on the other systems).
- `/dashboard` is a `_MOVED` redirect (`app.py:1288-1292`). Its `st.switch_page` drops the `#s-size`,
  so the Dashboard opens at the top.
- It also adds a history entry, so Back goes `/` → `/dashboard` → `/`: a loop.

**Code.** `src/ui/views/sector_view.py:290`, `page_href("dashboard")`.

**Proposed fix (by rule).**
1. `page_href` takes only addresses that are pages. The Dashboard is the root, so `page_href("")`
   should give `./` plus `?sys=` when it applies.
2. A test asserts that every `page_href(...)` argument is a `url_path` in `_PAGES`, never a `_MOVED` key.

**Correcting the address is not enough.** Opening `/#s-size` directly also lands at scroll 0: the
section is drawn after the browser has already tried the hash (probed: `#s-size` sits 5,293 px down
and the page stays at 0). A cross-page section link needs one of two things:
- a small script in a frame that scrolls the host to `location.hash` once the id exists (the way
  `screener_table` already injects into the host); or
- dropping the `#` and linking to the Dashboard page alone.

This is the only cross-page `#section` link on the site. The other 187 are in-page section links,
and every target id exists.

### Not faults (handled in the crawler)

  external list.

## Time (for the CI budget)

- **Clean run:** 555 s (9 min 15 s) with 4 browser contexts, against a server whose caches were partly
  warm. The first run took 809 s, cold and with module reloads.
- **Slowest pages:** the Dashboard, at 186-339 s per system. It is clicked once per system for the 11
  header and menu links, and the Portfolio page takes about 35 s to draw.
- **A cheaper CI run (suggestion):**
  - Click the header and menu once in total, not once per system. The b-check for page links never
    failed: the system rides in the session.
  - Click each stock-link pattern once per system rather than once per page.
  - This should come to about 5 min, at the cost of catching a page-specific nav fault only through
    the static href check.

## Not checked

- **Phone width (412 px):** not crawled. The 7 quick links are hidden below 1024 px and the menu
  popover is the only nav there. Menu links were clicked through their own handler (not visible at
  1400 px with the menu shut), not by opening the popover.
- **The Combined system** (`?sys=combined`): only reached through the "See it in Combined" links; not
  crawled as a source.
- **Whether a page drew the right system's data after a `?sys=` link:** only the address was checked,
  not the page's content.
- **The Screener's own filter links** (`?ind=`, and the filter writes that add history entries,
  `ranking_view.py:91-101`): only the stock page's "All N stocks on the Screener" link was clicked.
  Shared filter links wait for S198.
- **Rows in a table:** one row per table frame, and one link per href pattern per page. Other rows
  are assumed to behave the same.
- **Streamlit Cloud's `/~/+/` prefix and the outer frame:** this run was a bare local server, so
  relative-link behaviour under the prefix was not seen.
- **Live data (R2):** the app ran on release files; links that appear only with the live data were
  not seen.
- **Back after a full page load:** the stock pages and every `target="_self"` link are a new
  Streamlit session. Only the address was compared, not the restored state (widgets, open
  sections).
