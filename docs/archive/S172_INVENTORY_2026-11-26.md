## The plan for (b), and a suggestion

**As written in S172**, each of the 37 files would become its own R2 dataset, with its own publish step, its own audit and its own read through `src/storage`. That is 37 network reads on a cold start. It also means changing about a dozen workflows.

**Suggestion (recommended): one "app pack".**
- After each sync, the job that wrote any of the 37 files publishes one R2 dataset, `app/pack`. It is a zip of the 37 files at that commit, with each file's SHA-256 in its manifest.
- The app reads the pack once at startup through `src/storage`, checks every hash, and serves each file from it.
- The one fallback rule is the committed file, with the backup note (D3).
- Cost: one writer step and one reader. One R2 read instead of 37.
- What it gives up: a separate R2 history per file. git keeps that history anyway.

**The other way:** move the files one by one, as written. That gives each file its own revisions on R2, at 37 times the steps and the reads.

Not decided here: whether the pages may then stop the daily data commits. That would also end the daily Streamlit pull and the cache clear that comes with each one. Stopping those commits changes what git holds, so it is the owner's call.
